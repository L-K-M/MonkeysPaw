## 26. LLM settings sync decisions

Owner direction 2026-10-23: provider (LLM) settings sync across devices through
the sync account, including the API keys, protected by a dedicated encryption
key the owner provisions on each device — never the account password — with
last-writer-wins conflict resolution. These defaults resolve the remaining
ambiguities the same way §§19–23 record them. A slice that changes a contract
amends the referenced section in the same PR. S = provider settings sync.

| ID / gates | Ambiguity or conflict | Default |
|---|---|---|
| S1 · all | Provider settings are per-device today (§7.1); the feed model is path-based and cannot carry a singleton document. | One account-scoped document, outside the prompt feed. `GET /api/v1/me/provider-settings` returns `{rev, document, updated_at}` (`rev` 0 and null fields when absent). `PUT /api/v1/me/provider-settings {document}` is unconditional: the server stores the opaque ciphertext and returns the new `rev`. Revisions are a monotone ordering cursor only. |
| S2 · all | "Last writer wins" admits two readings once writes can race. | Literal arrival order wins: a pull precedes every push inside the same pass, so a device never overwrites state it has not seen; genuinely concurrent PUTs resolve by which commits last. No `base_rev` precondition and no 409 path exist. |
| S3 · all | Keys must sync but §12 never uploads secrets; the sync key must bootstrap manually, not from the account password. | One AES-256-GCM key (32 bytes) per sync account, generated on one device and entered on the others as a 43-character unpadded base64url string. It lives in the platform `SecretStore` under `provider-sync:<user ULID>`, follows the same tier/rollback rules as provider keys, and is never uploaded or logged. |
| S4 · all | The plaintext needs one portable shape on Foundation and kotlinx-serialization. | `{"version":1,"settings":<provider-settings.json object verbatim>,"secrets":{"provider:<uuid>":"<stored credential envelope>"}}`, encoded with the shared sorted-key profile. `settings` carries the whole stored object so unknown root/profile keys survive sync. `secrets` holds each referenced profile's persisted bound credential verbatim; origin/kind binding still validates on the receiving device because kind and base URL sync with the profile. |
| S5 · all | The wire needs versioning and ciphertext/account confusion needs ruling out. | `document` is unpadded base64url of `0x01 ‖ IV(12) ‖ ciphertext ‖ tag(16)`. AAD is `monkeyspaw/provider-settings/v1:` + the uppercase user ULID, so a ciphertext cannot be replayed under another account. Plaintext is capped at 256 KiB and secrets entries are bounded by the schema's key/value grammar. |
| S6 · all | A device that pulled a profile but has no local copy of its key must not strip the remote secret on its next push. | Push merges: for every profile with a secret reference, the secret is the locally persisted value when present, else the value carried in the last decrypted remote document. A reference cleared in metadata drops the secret (a deliberate Clear survives). A secret read that fails rather than returning nil aborts the step instead of uploading a doc with dropped keys. |
| S7 · all | Apply order can leave a dangling reference or an orphaned secret across a crash. | Apply writes secrets for the payload's referenced accounts and deletes local provider secrets whose accounts are no longer referenced, then commits the metadata object verbatim under the existing store lock/rollback contract. Orphaned ciphertext secrets without a profile are never usable; a profile missing its key reports the existing key-required state until the next pass. |
| S8 · all | Local state must know what was last synced and to which account it belonged. | `<data>/sync/provider-settings.json` is a version-1 `SyncPersistence` record `{version, server_url, user_id, rev, payload_hash}`: the last acknowledged rev and the SHA-256 of the last synced plaintext payload. A server/user mismatch resets the baseline (rev 0); the remote doc then applies when present, else the local document becomes the account's initial upload. Payload-hash comparison decides local dirtiness, so remote applies and unchanged files never re-upload. |
| S9 · all | The step must fit the pass's admission/revocation without weakening the journal contract. | The step runs inside the coordinator pass after the prompt push phase, under the same work permit and permitted client. The key check precedes the pull: without a provisioned key the account reports key-required and the endpoint is never contacted, so unprovisioned accounts keep syncing against servers that predate the routes. Transport/unauthorized errors propagate like any pass failure (offline retry or sign-in); decrypt, validation and apply failures become a typed outcome on the pass result and report, never a blocking prompt issue. A failed or skipped step leaves the record untouched so a later pass resumes from the last acknowledged rev. A remote document that fails authentication — sealed under a different key or corrupt on the wire — does not gate the push: per S2's literal last-writer-wins the local document overwrites it in the same pass, so key rotation or a recovered key self-heals on the next pass rather than stalling sync forever; the pass still reports the decrypt failure alongside the pushed state. A document that authenticates under the provisioned key but is not a readable v1 payload (oversized plaintext, unknown version, malformed shape) instead fails closed and blocks the push: authentication proves it belongs to this account's key and may be a newer client's format, so the pass reports decrypt-failed and preserves it rather than clobbering data it cannot read. A stored key of the wrong length fails closed before any request. |
| S10 · all | Settings edits should sync promptly without a second scheduler. | ProviderSettingsStore publishes change notifications after successful updates; composition observes them and calls the existing `localSave()` debounce. Remote applies also fire the notification; the payload-hash check makes the resulting pass a no-op, so no upload loop forms. |
| S11 · all | Syncing settings must not leak through diagnostics or the §12 scans. | Only the envelope crosses the wire; the server stores ciphertext it cannot read. Payload plaintext, keys and decrypted bytes never enter logs, reports, WorkManager input/output, saved state or diagnostics. The sync key's account belongs to the existing provider secret scans; revealed key text is shown only in the explicit settings field. |
| S12 · all | Sync of assistant credentials needs an owner-visible switch. | Settings → Assistant gains a "Provider settings sync" section: status, a Generate key action, an Enter key field, Reveal and Remove. The section is disabled while signed out or while a pass is resolving the account. Sync runs whenever a signed-in account exists and a key is provisioned; without a key the document can neither upload nor apply and the section reports key-required. |
